# llm-proxy-view 七项功能开源移植方案

**移植设计 · 基线 `2.4.0`（`309d259`）**

项目多了以后，用户仍能快速找到最近的会话。Claude Code 直连模型时，用户可以在本地查请求、算费用。离开电脑后，用户可以在飞书私聊里引用通知继续原会话。后台启动、会话自启动和一键更新共用一套服务生命周期。

## 移植范围与默认值

| 原编号 | 功能 | 开源版落点 | 用户何时感知 |
| --- | --- | --- | --- |
| 1 | 最近项目卡片和长尾列表 | Claude、Codex 各自生成视图数据，共用列表组件 | 升级 UI 后生效，最多 4 张卡片 |
| 2 | 复制日志 ID | 日志详情标题栏 | 升级 UI 后生效 |
| 3 | 飞书私聊通知与会话续接 | Claude Stop hook、现有飞书应用机器人与 Remote Bridge | 默认关闭，本机配置并启用后生效 |
| 4 | 文件读取与耗时补全 | Claude 文件采集器、现有日志和费用库、可选本地 OTLP 接收器 | 两项分别开启，新启动的 Claude 会话生效 |
| 5 | 默认后台启动 | `claude-proxy start` 和现有 Express 服务 | `start` 在服务就绪后返回，前台托管使用 `--foreground` |
| 6 | 会话自启动与 hook 去重 | Claude hook 安装、状态检查和 SessionStart 转发 | 新装 hooks 默认自启动，已有安装在用户执行修复时迁移 |
| 7 | 侧边栏更新 | npm 版本检查、受控安装、后台服务重启 | 默认每天最多自动检查一次，可关闭。安装由用户触发 |

Claude 与 Codex 只共用第 1 项的展示组件。飞书会话续接、文件采集、OTLP 和新增 SQLite 表均属于 Claude。

## 1. 两个 Dashboard 的项目概览

`DashboardTab` 已有按活跃度排列的 `sessionGroups`、按项目索引的事件和单独的 `orphanEvents`。`CodexTab` 从自己的 sessions、hooks 和 trace 时间线计算 `projectGroups`，无路径组里也可能有真实会话。分别从这两处取数，新增只接收行数据和交互回调的 `ProjectOverviewList`。排序沿用各页的最近活动时间，相同时间用稳定的项目键排序。

- 最近 4 个项目保留卡片。其余每行展示项目名、路径、最近会话或事件、会话数、已加载事件数和相对时间。项目行沿用卡片行为，进入最近会话。Claude 行保留有权限时的「新建远程对话」入口。长路径可查看全文，窄屏优先保留项目名、最近活动和操作。
- 纯孤立事件在卡片未满时占一张，满时进入列表末尾，点击可查看事件。Codex 有会话但无路径的分组仍可进入会话。两页继续使用各自的接口、SSE、详情面板和数据库。
- `Sidebar` 已有折叠交互，把偏好写入 `localStorage["claude-proxy.sidebarCollapsed"]`，不可用时回退内存状态。侧栏 188px 和内容区缩距作为独立样式改动，用窄屏和折叠态验收。

**验收**　两个页签分别覆盖 0、3、4、5、10 个项目，核对每个项目恰好出现一次。再覆盖孤立事件、未知目录的真实会话、长路径、刷新保留折叠状态，以及 SSE 到达后项目跨过第 4 名的情况。

## 2. 日志详情复制 ID

`LogDetailPanel` 打开时就有摘要行的 `id`，完整详情异步加载。复制按钮直接绑定当前选中行的完整 ID，点击成功显示「已复制」1.5 秒。快速切换详情时取消上一个按钮的反馈。按钮可用键盘操作，ID 过长时视觉截断，复制值始终完整。

优先调用 Clipboard API。权限被拒或局域网 HTTP 页面没有该 API 时，选中完整 ID 并提示手工复制。无需改查询接口或数据库。**验收**覆盖详情加载中、连续切换两条记录、复制失败和键盘操作，并用复制值查询原日志。

## 3. 飞书私聊通知与本地 Claude 会话续接

用户在本机完成一轮 Claude 对话后，选定的飞书应用机器人给本人发一条普通文本通知。用户在飞书消息菜单中点「回复」，输入「继续，把测试跑完」，Claude 就在原项目续接原会话。执行期间按该机器人的设置更新一张进度卡，最终答复作为普通私聊文本发送。用户可以直接引用这条最终答复继续下一轮。

**接入现有 Remote Bridge。** 开源版已有 `/cc continue-session`。在 `src/remote/feishu.ts` 中，`handleFeishuText` 接收飞书消息，`attachLocalSessionToFeishu` 绑定本地会话，`sendRemoteMessage` 负责投递。移植只需补上从 Stop 主动发通知、从引用找到原始 session、以及一次性消费通知三步。每个应用复用自己的 SDK client、WebSocket 和事件分发器。普通消息和 `/cc` 命令继续走原有处理分支。

| 配置与归属 | 设计 |
| --- | --- |
| 机器人与接收人 | 在 Dashboard 顶部的「飞书 → 配置」选择「可回复通知」。复用已配置的应用机器人，首次用私聊发送一次性绑定口令，自动记录接收人的 `open_id` 和私聊 `chat_id`。本地收到的通知只允许该接收人操作，同时遵守机器人的 `allowedUserIds`。 |
| 多机器人与项目 | 单个机器人可在本机选为其余允许项目的默认通知机器人。多机器人可分别绑定项目，按真实 cwd 精确匹配后优先使用项目绑定。匹配冲突在保存时指出。所有主动通知都要能确定唯一的机器人和接收人，续接始终使用通知记录里的 cwd。 |
| 配置与运行 | 沿用现有应用凭据、飞书长连接、`remoteBridge.claudeCommand` 和投递设置，默认走 `cli`。飞书通知面板显示私聊绑定状态，可发送测试消息。飞书总开关和事件选择控制推送，群 Webhook 与可回复通知择一投递。导入沿用 bot ID 与 appId 双重匹配的凭据规则，变更应用或收件人后须重新绑定私聊。 |

**消息如何找到原会话**

1. 在 Claude hook 入口处理通过本机受管 hook 身份校验的 `Stop` 和 `StopFailure`。校验完整 session ID、cwd 和该会话的 transcript，只提取项目名、会话标题、可见最终答复摘要或脱敏的失败原因。按项目选定通知机器人。Remote Bridge 自己执行的轮次由其最终回复路径交付，按本轮入站任务识别，避免额外发一张 Stop 通知。
2. 在 Claude 的 `logs.db` 追加 `feishu_resume_notices`，保存轮次、完整 session ID、cwd、`sourceBotId`、appId、接收人、chat ID、飞书消息 ID、一次性短码和状态。发送前登记本轮，发送成功后记录 `message_id` 并激活通知。旧通知被新一轮取代，迟到的发送回执按轮次处理。通知正文提示用户在飞书消息菜单中点「回复」并输入指令，服务通过原消息 ID 找到会话。
3. 在已有 `im.message.receive_v1` 入口优先保留审批回复和显式 `/cc` 命令。在普通消息查找最近线程之前，识别直接引用的 `parent_id` 或专用短码。已识别的续接消息必须同时匹配当前 bot、私聊 `chat_id` 和发送人的 `open_id`。群聊、他人转发、过期通知或空指令都不能触发续接。标明续接意图但校验失败时就地结束处理。其余消息沿用现有线程路由和当前机器人的 `defaultCwd`，切换活跃线程也不会改变旧通知指向的会话。
4. 以 `(sourceBotId, 入站 message_id)` 去重，事务内消费有效通知、锁定 session 并登记待投递消息。沿用 `attachRemoteSession` 的目录校验和显式线程绑定，以持久化的消息 ID 调用既有投递流程。把登记与启动子进程分开，提交后再投递。服务重启时可恢复已登记待投递的消息，执行结果不明的任务标为中断，由用户核对后重试。重复回调复用同一入站任务和进度卡。
5. 正常交付使用原机器人的 `sourceBotId`、原私聊和既有进度卡更新逻辑。让发送最终文本的 helper 返回飞书消息 ID，把本轮最终文本与下一轮通知关联。长回复分段时，各段引用指向同一条可消费记录。显式 `remote_reply` 优先，CLI 结果和子进程 Stop 共用本轮交付状态，避免双发。发送使用普通聊天消息，用户端的引用无需机器人发话题回复。对话诊断仅记录阶段和标识，应用密钥及会话正文不进入诊断日志。

**验收**　在已有飞书测试应用的私聊里走通「本地 Stop → 收到通知 → 引用并输入指令 → 原 session 执行 → 进度卡更新 → 普通文本最终答复 → 引用答复再续一轮」。用两个机器人的事件样本验证相同短码、错 bot、错收件人、群聊转发、旧卡片、消息重投、并发回复和服务重启。回归 `/cc continue-session`、审批回复、无引用私聊、既有群聊命令和显式 `remote_reply`。停用某机器人的本地通知后，该机器人的常规远程对话仍可用。

## 4. Claude 文件采集、请求去重与耗时

配置页和新增的 `claude-proxy raw-bodies install|uninstall|status` 共用一套安装逻辑。开启时在用户级 Claude settings 中设置 `OTEL_LOG_RAW_API_BODIES=file:<目录>`，默认目录为 `~/.claude-proxy/raw-api-bodies/`，权限限当前用户。保留现有模型地址、认证和路由设置。官方将成功响应的 `index.jsonl` 列为 Claude Code **2.1.274 起**提供的文件接口。状态页区分「未启用」「等待新会话首条索引」「正在采集」「版本或配置冲突」。开关旁说明原始文件包含会话历史和工具结果。[Claude Code Monitoring](https://code.claude.com/docs/en/monitoring-usage#api-response-body-event)

**摄取与恢复。** 单个服务实例每 2 秒扫描一次，按文件身份和字节偏移读取已换行的索引记录，把待配对的记录与游标一并持久化。遇到半行留给下轮，遇到索引截断或替换重新识别文件，以请求标识去重。这样不必假设 Claude 每次追加都会重新打开索引。为工具拥有的索引设置低流量时的轮换与旧段清理，轮换需验证对应 Claude 版本的写入行为。未验证时只跟读并提示占用。每轮限制处理时间，分批等待独立落盘的 request/response。超时先标记「响应未齐」，迟到文件补全原记录。只有请求文件的孤儿按文件身份登记，区别于上游明确返回的请求错误。

读写只接受采集根目录内、符合命名约定的普通文件，拒绝越界路径和符号链接。对索引行、正文和 transcript 分别限长，验证结构并剔除可能包含 Claude 隐藏推理的块后才写日志、diff 或 SSE。尊重 `logCollection` 的采集开关和条数裁剪。关闭原始请求体采集时，文件正文也不能通过 `modifiedRequestBody` 或 diff 绕回。只有写库和游标提交成功后才清理本工具目录中的已处理文件。卸载只撤销仍匹配本工具所写值的键，并提示已打开的 Claude 会话需重启。

**日志与计费。** 改动集中在 `src/core/proxy.ts`、`src/storage/logs.ts`、`src/cost/capture.ts` 和 `src/storage/cost.ts`。当前代理用本地 UUID 作 `logs.id`，文件索引用上游 `request_id`，两者含义不同。`initCostCapture` 只处理完成的 update，而 `createCostRecord` 每次生成新 UUID。以下改动一起交付，以免 Dashboard 显示一份请求、预算却计算两次。

| 变化 | 落点与规则 |
| --- | --- |
| 来源和关联字段 | 给 Claude 日志增加 `source`、`querySource`、`upstreamRequestId` 和响应 message ID。旧行按 `proxy` 读取。文件行使用保留的目标标识 `file-capture`，显示「文件读取」，可按来源筛选。保留当前日志 ID 对外协议。 |
| 双来源合并 | 代理从上游响应头或响应消息记录真实标识。以同一会话内的上游请求 ID 优先匹配，缺失时仅用唯一的响应 message ID。代理和文件谁先到都合并到同一逻辑请求，保留代理的路由、HTTP 状态和实测耗时。并发时由数据库唯一键仲裁。时间窗口只供排查。缺少可靠标识且有重叠候选时暂缓该文件行计费，保留待核对数量。 |
| 一次计费 | 抽出按逻辑日志 ID 幂等的费用写入，覆盖首次即完成、响应晚到、跨源合并及重试。迁移先处理历史重复的非空 `logId` 再建部分唯一索引，保留无 `logId` 的历史记录。文件记录用索引或响应的真实模型定价。日志、费用与消费状态在同一事务提交，SSE 和预算提醒在提交后按实际变化发送。 |
| 展示与归属 | 原始文件缺少 HTTP 状态、响应头和 SSE 明细时显示「未采集」。旧表的 `responseStatus`、`durationMs` 有非空约束。为文件来源加耗时是否已采集的标志，缺失时 API 返回 null，UI 显示「—」，SQL 平均值只统计有观测值的行。cwd 先走 `resolveSessionCwd`，再取同会话最早带 cwd 的 hook，仅回填空值。可用 `message_uuid` 或 `message_id` 在该会话的 subagent transcript 中找类型，无法确认时保留原 `query_source`。 |

**可选耗时补全。** 单独开启后才配置本机 OTLP HTTP/JSON 日志端点 `/api/otel/v1/logs`。由安装器配置 `CLAUDE_CODE_ENABLE_TELEMETRY`、`OTEL_LOGS_EXPORTER`、`OTEL_EXPORTER_OTLP_LOGS_PROTOCOL` 和 `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`。写入前先检查已有通用及 logs 专用配置。冲突时保留原值，文件采集仍可独立工作。接收器只取 `api_request` 的请求标识和耗时，限制请求大小，忽略其他属性。先到的元数据可缓存 15 分钟、最多 5,000 条，后到的按请求 ID 更新已有行，不重复计费。只接收本机的 OTLP 请求。仅在收到可信的首 token 耗时（TTFT）时填入该值。换端口和卸载时按逐键所有权恢复用户设置。[Claude Code Monitoring](https://code.claude.com/docs/en/monitoring-usage#api-request-event)

**验收**　用脱敏 fixtures 覆盖半行、乱序、超大文件、目录越界、索引重放、崩溃重启、迟到响应、同会话一秒内多次调用，以及代理先到和文件先到。对相同请求核对日志条数、费用总额与预算通知次数。为两个不同请求核对均被保留。最后用支持版本的 Claude Code 在临时配置目录运行一轮直连和一轮双来源采集，分别核对项目、模型和 token 用量。

## 5. 后台启动与服务身份

把 `src/cli/commands/start.ts` 的启动过程拆成前台运行服务和启动器两条路径。前台继续调用 `startServer`。后台启动器用当前 Node 和实际 CLI 入口派生前台子进程，继承 host、port、UI、verbose 与状态栏偏好，将输出追加到 `~/.claude-proxy/server.log`。启动时超过 5 MB 则轮换一份。子进程关闭标准输入，父进程在就绪后退出。macOS 状态栏只由一个启动者在就绪后拉起。

- `/health` 目前仅返回状态和时间。增加固定服务名、版本和本次启动实例 ID，保留现有字段。新子进程由启动器传递实例 ID。重复启动按服务名和端口识别既有实例。占用端口的旧版或其他程序身份不明时，返回提示并保留该进程。
- 并发启动必须只有一个实例初始化飞书连接、费用监听和文件采集。先取得端口或启动锁，再启动有副作用的服务。启动器等待就绪最多 20 秒。遇到地址竞争复查胜出者，子进程提前退出则给出本次日志尾部。对通配监听地址使用对应的回环地址探活。`--check` 静默且不重新拉起状态栏。
- 普通关闭、SIGTERM 和升级重启共用一次有界清理，停止接收新任务，保存飞书待投递消息，关闭机器人连接并清理文件采集器和 Codex 资源。无参 `start` 与 `start --background` 等价。后台子进程和需要前台托管的部署显式使用 `--foreground`。

**验收**　在临时数据目录验证关终端后仍能访问、重复启动、同时启动、端口被其他程序占用、启动超时、日志轮换、前台 Ctrl+C、Dashboard 关闭服务。macOS 验证状态栏只出现一次。Windows 后台启动单独验证 `windowsHide` 和子进程退出，发布支持矩阵以实测为准。

## 6. SessionStart 自启动与 hook 去重

2.4.0 给每个受管事件安装 HTTP hook，并按整组标记清理。用户 hook 和受管 hook 混在一个组时，整组删除会误删用户内容。Claude Code 当前对 SessionStart 列出的处理器是 command 与 MCP，且匹配的 hooks 并行运行。把这个事件改为**唯一一个受管 command hook**，由它负责转发，避免冷启动时漏一次、补发时又多一次。[Claude Code Hooks](https://code.claude.com/docs/en/hooks#sessionstart)

| 安装后的状态 | SessionStart command 的动作 |
| --- | --- |
| `autoStart=true` | 从 stdin 接收事件，调用第 5 项的就绪逻辑，服务可用后向回环地址的 `/api/hooks/SessionStart` 转发一次。热启动直接转发。 |
| `autoStart=false` | 只向已运行的服务转发一次。服务关闭时快速返回。 |
| 未安装 hooks | 切换偏好只保存本机设置。用户安装或修复时才写入 Claude settings。 |

建议由 `claude-proxy hook forward SessionStart --port <port>` 读取和转发 stdin，仅在启用自启动时调用静默的 `start --check` 就绪逻辑。命令固化 Node 和 CLI 的绝对路径并按平台转义。stdout 保持为空，有界超时，诊断写 stderr。快速失败允许 Claude 会话继续启动。转发如需重试，以本次调用 ID 做服务端去重，同一 session 合法的 resume 或 clear 仍各自入库。`hook status` 和 Dashboard 使用同一判定，检查每种受管事件的类型、数量、端口，以及自启动可执行路径是否仍存在。nvm 换版本或 npx 缓存被清理时显示可修复原因。

安装、修复和卸载改为**逐条**识别。优先认领 `_managedBy`。标记丢失时只认领精确匹配旧版生成形态、回环地址、受管事件名与路径的条目，带自定义 header、matcher 或额外命令的歧义项保留并报告。组中其余 hook、用户顺序和 matcher 原样保留。SessionStart 旧 HTTP 项替换为命令，其他事件沿用既有投递方式。`autoStart` 属于本机偏好，配置导入时保留本机选择。

第 4、6 项和现有代理接入都会改 Claude settings。统一使用 `src/lib/claude-settings.ts` 的读改写入口，支持实际 Claude 配置目录，区分文件缺失和 JSON 损坏。同一设置文件的 CLI 与 Dashboard 写入串行化，持锁后重读，只改目标键，再以同目录临时文件原子替换。状态读取失败时显示原因。

**验收**　从 2.4.0 设置样本升级，覆盖重复安装两次、标记丢失、混合用户 hook、端口变化、开关切换和卸载。并发打开两个会话应启动一个服务并收到各自的一条 SessionStart。交错执行 hook 安装、文件采集开关和代理配置，逐键比对用户原设置。

## 7. 侧边栏检查更新与一键更新

现有 `package.json` 已声明公共 npm `publishConfig.registry`。从该 registry 查询固定包 `llm-proxy-view` 的 `latest`，只接受合法的稳定版本，使用同一 registry 安装已确认的精确版本。自动检查由本机偏好 `updateCheck` 控制，默认开启，缓存成功结果 24 小时，支持手动刷新。并发请求共用一次查询，离线时显示上次成功结果与时间。

- **能力判断。** `GET /api/query?type=update-status` 返回当前版本、可用版本、检查时间、安装能力和原因。首版一键安装面向 macOS/Linux 上由本工具后台启动、且能确认归属的 npm 全局安装。用同一 Node 配套 npm 的 `root -g`、prefix、包真实路径和 CLI 指向交叉验证。源码、npx、npm link、其他包管理器、前台托管或 Windows 展示适合当前安装方式的手动升级指引。[npm 全局目录](https://docs.npmjs.com/cli/v9/configuring-npm/folders/)
- **操作边界。** `POST /api/set` 新增 `checkUpdate` 和 `installUpdate`。现有 Express 中间件已拦部分跨站写入。本机管理操作另校验连接来自回环、Host 属于本地允许值、Origin 与预期 Dashboard 精确匹配。飞书续接配置、采集开关和能改变这些权限的配置导入复用同一边界。安装参数由服务端确定，客户端只提交希望安装的已展示版本。安装前重查，版本变化时返回新版信息供重新选择。
- **安装与切换。** 每个安装前缀只允许一个更新任务。用服务当前 Node 配套的 npm、固定包名和版本执行，限时 5 分钟。先验证写权限、目标 Node 兼容性和任务状态。有活动远程任务时显示占用，等任务结束再由用户触发。开始切换后暂停接收新的远程执行任务，防止检查空闲后又启动新任务。安装成功后用新包做 CLI 和原生 SQLite 加载预检，再让独立重启进程按原 host、port、UI、verbose 和状态栏设置拉起服务。页面只在目标版本、服务身份和新实例 ID 均就绪时刷新。
- **失败与恢复。** 检查失败保留缓存，安装或预检失败保留运行实例并报告失败阶段。安装可能已改动磁盘上的包，记录升级前版本、前缀和恢复命令。新进程起不来时，独立重启进程把错误写入本地日志，并给出恢复旧包再启动的指令。发布升级涉及 SQLite 迁移时，在新版本打开数据库前生成一致性备份，并明确恢复数据的时点。

**验收**　测试版本比较、离线缓存、并发检查、跨站与非本机写入、安装归属、重复点击、安装失败和就绪超时。端到端用两个测试版本、临时 npm prefix、隔离的数据目录与端口，验证能从旧版本更新至新版本、设置沿用、SQLite 可读，并实际演练恢复。运行时 Node 范围同时核对锁定版 `better-sqlite3`，仅有全局 `fetch` 不能证明版本兼容性。
